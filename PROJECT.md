# PROJECT

## 1. Цель проекта

Цель проекта

Создать эталонный B2B-сайт производителя мебельных опор VELES LEGS на платформе InSales.

Проект должен отвечать следующим требованиям:

• максимальная скорость загрузки;
• максимально простая поддержка;
• стабильная работа после обновлений InSales;
• единый стиль оформления;
• высокая конверсия;
• соответствие современным требованиям SEO;
• соответствие требованиям Schema.org;
• соответствие требованиям Accessibility;
• отсутствие дублирования кода;
• модульная архитектура.

Главная задача проекта — создать систему, которую можно развивать годами без полной переделки.

Каждый элемент сайта должен быть независимым модулем.

Любое изменение должно затрагивать только тот модуль, который изменяется.

Любое решение должно быть масштабируемым.

Проект не допускает временных решений, костылей и дублирования логики.

Качество архитектуры важнее скорости разработки.

## 2. Философия проекта

Данный проект создаётся не как обычный интернет-магазин.

Это долговечная промышленная платформа производителя мебельных опор.

Главные принципы проекта:

• скорость выше эффектов;
• стабильность выше красоты;
• простота выше сложных решений;
• отсутствие дублирования кода;
• отсутствие временных решений;
• каждое изменение должно улучшать архитектуру;
• каждая функция должна быть понятной;
• минимальная зависимость от платформы;
• отсутствие хаотичных стилей;
• отсутствие конфликтующих CSS;
• отсутствие дублирующихся JavaScript;
• отсутствие магических чисел;
• единая система именования.

Сайт должен оставаться обслуживаемым через 5, 10 и более лет.

Любое изменение сначала оценивается по следующим вопросам:

1. Делает ли это архитектуру проще?
2. Делает ли это сайт быстрее?
3. Делает ли это код понятнее?
4. Не создаёт ли это будущих проблем?

Если хотя бы один ответ отрицательный — изменение запрещено.

## Основные правила разработки

На протяжении всего проекта действуют следующие обязательные правила.

### 1. Запрещено

• дублировать CSS;
• дублировать JavaScript;
• дублировать HTML;
• создавать вторые версии уже существующих компонентов;
• копировать одинаковые блоки;
• создавать "временные" решения;
• использовать !important без крайней необходимости;
• изменять рабочий код ради экспериментов.

### 2. Разрешено

• рефакторинг;
• упрощение архитектуры;
• объединение повторяющегося кода;
• уменьшение размера файлов;
• повышение скорости загрузки;
• улучшение SEO;
• улучшение доступности;
• улучшение читаемости.

### 3. Перед любым изменением

Необходимо определить:

— что именно меняется;
— почему меняется;
— какие файлы будут затронуты;
— какие риски существуют.

### 4. После любого изменения

Обязательно проверить:

• отсутствие ошибок;
• отсутствие сломанной верстки;
• отсутствие ухудшения производительности;
• отсутствие конфликтов CSS;
• отсутствие конфликтов JavaScript.

Любой код должен оставлять проект лучше, чем он был до изменения.

## Архитектурные принципы

Архитектура проекта должна соответствовать следующим требованиям.

### Модульность

Каждый элемент сайта является самостоятельным модулем.

Изменение одного модуля не должно влиять на остальные.

### Независимость

Каждый CSS-файл отвечает только за свою область.

Каждый JavaScript отвечает только за свою функциональность.

Запрещено создавать зависимости между независимыми блоками.

### Предсказуемость

Каждый разработчик должен понимать назначение любого файла за несколько минут.

Если файл невозможно быстро понять — архитектура считается нарушенной.

### Минимизация

Каждая строка кода должна иметь смысл.

Любой повторяющийся код обязан быть вынесен в общий модуль.

### Совместимость

Все изменения обязаны сохранять совместимость с платформой InSales.

Нельзя использовать решения, требующие изменения ядра платформы.

### Производительность

Каждый новый компонент должен оцениваться по влиянию на:

• скорость загрузки;
• количество запросов;
• размер CSS;
• размер JavaScript;
• CLS;
• LCP;
• INP.

Если компонент ухудшает производительность без объективной причины — он не принимается.

## Политика внесения изменений

Любое изменение проекта проходит через четыре обязательных этапа.

### Этап 1. Анализ

Перед изменением необходимо определить:

• какие файлы будут изменены;

• почему необходимо изменение;

• существуют ли уже похожие решения;

• можно ли использовать существующий код вместо создания нового.

Если существует готовое решение, запрещается создавать ещё одно.

---

### Этап 2. Проектирование

До написания кода необходимо определить:

• какие блоки будут затронуты;

• какие последствия возможны;

• как изменение повлияет на скорость сайта;

• как изменение повлияет на SEO;

• как изменение повлияет на мобильную версию.

---

### Этап 3. Реализация

Во время реализации запрещается:

• менять несвязанные участки кода;

• выполнять массовое форматирование;

• переименовывать файлы без необходимости;

• удалять комментарии;

• изменять рабочие блоки ради "красоты".

Изменяется только то, что относится к поставленной задаче.

---

### Этап 4. Проверка

После завершения необходимо убедиться, что:

• сайт отображается корректно;

• мобильная версия не нарушена;

• изображения работают;

• цены отображаются;

• кнопки работают;

• формы работают;

• JavaScript не содержит ошибок;

• CSS не содержит конфликтов;

• SEO не ухудшилось.

Любое изменение считается завершённым только после успешного прохождения проверки.
